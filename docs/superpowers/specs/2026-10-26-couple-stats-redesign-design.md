# Kaspi Tracker: статистика, приложение для пары, редизайн — дизайн

Дата: 2026-10-26. Статус: черновик на согласование.

Пометка **[решение Claude]** — выбор, который сделал я, а не пользователь; его можно оспорить. Всё остальное — со слов пользователя.

## Зачем

Приложение сейчас личное: один человек, один телефон. Пользователь хочет:

1. Видеть год по месяцам — сколько тратил и получал — и общую статистику «в среднем в день / неделю / месяц».
2. Пользоваться приложением вдвоём с девушкой: каждый видит свои траты, её траты и общие траты пары.
3. Уйти от текущего вида, который читается как «AI-слоп» (фиолетово-синий градиент, свечения, блики), к тёплому, уютному дизайну.
4. Убрать бюджеты (лимиты по категориям) — они не нужны.

Успех: вечером открываешь приложение, переключаешь «Я / Она / Вместе» и видишь честные цифры — свои, её и общие — без задвоений; в «Статистике» видно, как менялись траты по месяцам.

## Цели

- Новая вкладка «Статистика».
- Пара: связь двух телефонов кодом, синхронизация через Supabase, переключатель «Я / Она / Вместе», пометка операций «своё / общее», массовая пометка.
- Удаление бюджетов целиком.
- Редизайн по макетам из Claude Design (промт: `docs/claude-design-prompt.md`).

## Не цели

- iOS, веб-версия. У обоих Android и Kaspi, ставится один и тот же APK.
- Больше двух человек в паре, несколько пар.
- Правка чужих операций. Партнёр — только просмотр.
- Общие лимиты/бюджеты — бюджетов нет вообще.
- Регистрация по почте/паролю.
- Синхронизация в реальном времени (секунды). Достаточно «обновилось при открытии / в течение ~15 минут».

## Анти-цели (что сделает работу провальной, даже если «работает»)

- **Потеря истории.** Room до сих пор с `fallbackToDestructiveMigration()`: любая версия схемы без своей `Migration` молча стирает базу. Каждая смена схемы — явная миграция + тест; перед установкой на живой телефон — снять копию базы (см. `FEATURES.md`, раздел 12).
- **Задвоение денег** в любом виде: одна операция не должна попасть в итог дважды ни в «Я», ни в «Вместе».
- **Приложение перестаёт работать без интернета.** Локальная база остаётся главным источником; облако — только для обмена с партнёром. Без сети и без пары всё работает как сейчас.
- **Утечка данных** посторонним. Ключ Supabase из APK не должен давать доступа к чужим строкам.
- Новый дизайн, снова похожий на шаблон (градиенты, свечения, всё одинаковое).

## Ограничения

- Kotlin, Jetpack Compose, Material 3, Room 2.6.1, minSdk 26, targetSdk 35. Сборка без `gradlew` — через wrapper-jar и JBR из Android Studio (см. память проекта / `FEATURES.md`).
- Текущая версия БД — 6.
- Живой телефон пользователя — Samsung Galaxy A36 (Android 16), агрессивно усыпляет фон.
- У пользователя уже есть аккаунт Supabase; бесплатный проект замораживается после ~7 дней без запросов.
- Существующие 124 юнит-теста должны остаться зелёными; логика новых частей — с юнит-тестами на fake DAO, как сейчас (`FakeDaos.kt`).

## Часть 2. Вкладка «Статистика»

Нижнее меню: **Обзор · Статистика · Аналитика · История** **[решение Claude: порядок]**.

Все цифры — только операции с суммой, без `excludedFromStats` (переводы между своими картами, возвраты), как везде в приложении. Учитывает переключатель «Я / Она / Вместе» (часть 3).

**Год по месяцам**
- Выбор года стрелками ‹ 2026 ›; доступны годы, где есть операции.
- По каждому из 12 месяцев: потрачено, получено. Будущие месяцы — пустые, не нули в графике.
- Итог года: потрачено, получено, разница; средний месяц (по месяцам, где были операции); самый дорогой месяц.
- График (парные столбцы трата/доход или как нарисует дизайн) + список месяцев с цифрами.
- Тап по месяцу → История с фильтром на этот месяц (существующий механизм `Routes.history(...)` с `from/to/period`; категория при этом не задаётся — маршрут нужно научить принимать период без категории).

**Общая статистика**
- Средняя трата в день, в неделю, в месяц. База — от даты первой операции в истории выбранного вида до сегодня, а не от 1 января **[решение Claude]**.
- По дням недели (Пн…Вс) — **переезжает сюда из Аналитики**, в Аналитике убирается **[решение Claude]**.
- По неделям: последние 12 недель.
- Самый дорогой день за всё время (дата + сумма).
- Дней без трат (с первой операции).
- Всего потрачено / получено за всё время.

Аналитика остаётся как есть (периоды, сравнение месяцев, категории, топ мерчантов), минус блок «по дням недели».

Расчёты — чистые функции в отдельном файле (по аналогии с `MonthForecast`), с юнит-тестами: границы месяцев/недель в часовом поясе устройства, пустая история, год без операций.

## Часть 3. Приложение для пары

### Как это выглядит для пользователя

- Каждый ставит тот же APK на свой телефон. Свои операции телефон, как и сейчас, ловит из уведомлений Kaspi, чеков и ручного ввода.
- Экран «Пара»: своё имя (и цвет), статус связи, «показать мой код» (6 цифр + QR), «ввести код партнёра», «отвязать».
- Связка: один показывает код, второй вводит. Код одноразовый, живёт ~10 минут **[решение Claude]**. QR — тот же код; сканер QR — по желанию исполнителя, ввод цифр обязателен.
- Переключатель **Я · Она · Вместе** на Обзоре, Статистике, Аналитике, Истории. Подписи — имена из профилей («Она» — условное название в документе). Выбор запоминается между запусками **[решение Claude]**. Пока пары нет, переключатель скрыт.
- **«Своё / общее».** Пометку ставят сами пользователи, вручную. По умолчанию — «своё». Каждый помечает только свои операции **[решение Claude]**.
  - Одна операция — в листе редактирования.
  - Пачка — долгий тап в Истории (и в «Последних операциях» на Обзоре) включает режим выбора: галочки, тап по заголовку дня выбирает весь день, сверху «Выбрано: N» и сумма выбранного, действия «Общее», «Своё», «Категория», «Удалить» (с подтверждением). Выход — крестик / «Назад». Этот режим полезен и без пары (массовая смена категории/удаление).
  - Подсказка по магазину **[решение Claude]**: приложение запоминает последнюю пометку «общее/своё» для ключа мерчанта (`MerchantKey`), как сейчас запоминает категорию, и ставит её новым операциям этого мерчанта. Отключается переключателем на экране «Пара». Массовая пометка тоже обучает. Если пользователю это не понравится — легко убрать.
- **Что показывает каждый вид:**
  - **Я** — все мои операции, как сейчас.
  - **Она** — все её операции, только просмотр: нет листа редактирования, нет режима выбора, нет очереди «Разобрать», нет инструментов.
  - **Вместе** — **только операции, помеченные «общее»**, мои и её. Итог, сколько внёс каждый (₸ и %), категории, графики. В строке операции видно, чья она (аватар/инициал/цвет). В режиме выбора выбираются только мои строки.
- Переводы между нами отдельно не обрабатываются: в «Вместе» попадает только то, что вручную отмечено «общим», так что задвоение возможно, только если кто-то сам пометит перевод партнёру как общий **[решение Claude: не детектить переводы между партнёрами]**.
- Остатки на картах: в «Я» — мои, в «Она» — её, в «Вместе» блок скрыт **[решение Claude]**.
- Подписки, Правила категорий, Разобрать, Импорт чеков, Бэкап, Журнал — только свои данные, переключатель на них не влияет.
- Отвязка: подтверждение → связь удаляется на сервере; у обоих при следующей синхронизации локальная копия данных партнёра стирается, переключатель пропадает. Свои данные у каждого остаются.

### Синхронизация через Supabase

**Аутентификация.** Анонимный вход Supabase (anonymous sign-in) при первом запуске, без экранов регистрации. Сессия хранится на устройстве. **Риск:** переустановка приложения или «очистить данные» = новый анонимный пользователь = связь с партнёром теряется, свои облачные строки остаются сиротами. Решение для v1: после переустановки — восстановить свои данные из локального бэкапа и связаться заново; облачные «сироты» не мешают **[решение Claude]**. Привязка к Google-аккаунту — не в этой версии.

**Схема в Supabase** (набросок, детали — исполнителю):
- `profiles` — `user_id` (= `auth.uid()`), `display_name`, `color`.
- `couples` — `id`, `user_a`, `user_b`, `created_at`. Пользователь — максимум в одной паре.
- `pair_codes` — `code`, `user_id`, `expires_at`. Погашение кода — RPC-функция (`security definer`), которая проверяет срок, создаёт `couples` и удаляет код; клиент не читает чужие коды напрямую.
- `transactions` — `id uuid` (генерируется на телефоне), `user_id`, `timestamp`, `amount`, `type`, `merchant`, `category`, `account`, `balance`, `source`, `shared`, `excluded_from_stats`, `updated_at`, `deleted` (мягкое удаление).
- **RLS:** вставка/изменение — только `user_id = auth.uid()`; чтение — свои строки и строки партнёра по `couples`. Профиль партнёра — чтение. После отвязки чтение партнёрских строк сразу перестаёт работать.

**Что уходит в облако:** операции (поля выше). **Не уходят** `rawText`, `title`, `dedupKey`, правила категорий, бэкапы **[решение Claude: меньше личных данных на сервере; для просмотра партнёру они не нужны]**.

**Локально:**
- В `transactions` новые столбцы: `uuid` (стабильный id для облака; для существующих строк генерируется миграцией), `shared` (Boolean, default false), `updatedAt`, `syncedAt`/признак «грязная» и мягкое удаление (или отдельная таблица «удалить на сервере») — точный механизм на выбор исполнителя.
- Операции партнёра — **отдельная таблица** `partner_transactions`, только чтение **[решение Claude]**: все существующие запросы (подписки, очередь разбора, самопереводы, дедуп, журнал) продолжают видеть только свои данные без правок.
- Правила «своё/общее» по мерчанту — отдельная таблица или столбец в `category_rules`, на выбор исполнителя.
- Все изменения схемы — одна миграция 6→7 (вместе с удалением `budgets`) с тестом.

**Облако — только пока есть пара** **[решение Claude]**. Анонимный вход происходит при первом запуске, но ни одна операция не уходит на сервер, пока пары нет. После связки выгружается вся история; при отвязке серверная функция удаляет пару и **все облачные операции обоих**, каждый телефон стирает локальную копию данных партнёра. Новая связка с кем-то другим начинается с чистого листа.

**Когда синхронизируется (пока пара есть):** при открытии приложения, после каждой своей вставки/правки/удаления (с небольшой задержкой, чтобы пачка ушла одним запросом), и периодически через WorkManager (минимум 15 минут, только при наличии сети). Толкаем свои «грязные» строки, тянем строки партнёра с `updated_at` новее последней загрузки. Конфликтов нет: каждую строку пишет только её владелец.

**Первая связка:** после связи каждый выгружает всю свою историю, так что «Вместе» сразу показывает прошлые месяцы (там, где уже есть пометки «общее»).

**Ключи:** URL проекта и anon-ключ — в `local.properties` → `BuildConfig`, в git не попадают **[решение Claude]**. Таблицы и RLS — SQL-миграцией в репозитории (например, `supabase/migrations/…sql`), чтобы схему можно было накатить в панели Supabase.

**Настройка проекта (решено с пользователем):** пользователь создаёт **новый отдельный** проект Supabase только под это приложение и передаёт URL + anon-ключ. SQL схемы, RLS и включение анонимного входа описываются в репозитории; применяет их пользователь в панели Supabase (или выдаёт доступ через Supabase CLI). Связка и RLS проверяются вживую на двух устройствах: телефон пользователя + второе устройство (телефон девушки по adb или эмулятор), включая проверку, что третий анонимный пользователь не читает чужие строки.

**Клиент:** официальный Kotlin-клиент Supabase (`supabase-kt`: auth + postgrest). Версию и совместимость с Kotlin/Ktor проекта проверить по актуальной документации, не по памяти.

**Статус и ошибки:** на экране «Пара» — «последняя синхронизация: …», ошибка сети не ломает приложение; если проект Supabase заморожен — понятное сообщение («сервер спит, разбуди проект в панели Supabase»).

### Онбординг **[решение Claude]**

Входит в объём, но делается на шаге редизайна (5), сразу в новом дизайне. Поток: что делает приложение → доступ к уведомлениям → снять ограничения батареи → своё имя → связаться с партнёром (можно пропустить). Показывается один раз; на уже установленном телефоне пользователя — не показывается. До редизайна имя и цвет задаются на экране «Пара», анонимный вход идёт молча при запуске — онбординг потом просто переиспользует эти же действия.

## Часть 4. Редизайн

- Источник — макеты Claude Design по `docs/claude-design-prompt.md`. Пользователь сгенерирует их и передаст (экспорт / скриншоты / токены).
- Переносим: палитру светлой и тёмной темы, цвета категорий, цвета «я / она / вместе», шрифты, отступы, радиусы — в `ui/theme/*`; компоненты — в `ui/components/*`. Старый декор (`GlowOrbs`, `ShineSweep`, hero-градиент, `topHighlight`) удаляется, если в макетах его нет.
- Новые экраны (Статистика, Пара, режим выбора, онбординг) верстаются сразу в новом дизайне.
- Проверка — на живом телефоне через adb-скриншоты в обеих темах: пустые состояния, загрузка, ошибки, длинный контент.

## Порядок работ

1. Удаление бюджетов + миграция 6→7 со всеми новыми столбцами (один раз трогаем схему).
2. Логика статистики (чистые функции + тесты).
3. «Своё/общее» локально: столбец, массовый выбор в Истории, подсказка по мерчанту — полезно и без пары.
4. Supabase: схема + RLS, анонимный вход, связка кодом, синхронизация, `partner_transactions`, режим «Я/Она/Вместе» во ViewModel'ях.
5. Редизайн — когда придут макеты. Пункты 1–4 до этого делаются на текущих компонентах с минимальным UI; экраны потом перекрашиваются, а не переписываются.

Пункты 1–4 не ждут дизайна.
