## 1. Как приложение получает данные

Три независимых источника, каждый пишет в одну таблицу `transactions`.

### 1.1 Автоматически — уведомления Kaspi

`service/KaspiNotificationListener.kt` — `NotificationListenerService`, слушает пуши пакета `kz.kaspi.mobile`. Работает только пока у приложения есть доступ к уведомлениям (выдаётся вручную в настройках Android) и пока систему не убила батарея.

Что ловится: покупки картой, пополнения, переводы — всё, на что Kaspi шлёт push с суммой. **Не ловится**: оплаты по QR внутри самого приложения Kaspi (автобус, магазины по QR-коду) — Kaspi на них push с суммой не присылает, только чек. Из проверки на реальных данных пользователя: из 60 последних чеков ни один не имел парного push.

`parser/KaspiNotificationParser.kt` разбирает текст push:
- сумма — regex на число + валютный маркер (₸, тг, тенге, KZT), с обработкой разных пробелов-разделителей тысяч и обеих десятичных запятых;
- тип операции (покупка / перевод исходящий / перевод входящий) — по ключевым словам;
- **мерчант/контрагент** — берётся со строки под суммой (Kaspi всегда пишет тремя строками: "Покупка: X ₸" / "КОНТРАГЕНТ" / "Доступно: Y ₸"), с отсечением комментария после `:` ("Татьяна Ц.: за Алису" → "Татьяна Ц.");
- **счёт** — из заголовка push, только если это реальное название карты ("Kaspi Gold"), а не маркетинговый заголовок вроде "Kaspi.kz";
- **остаток на карте** — из строки "Доступно: X ₸".

Дедупликация: Kaspi отправляет одну операцию как минимум двумя push подряд (сводка группы + сама карточка, разница миллисекунды–секунды, разные заголовки). `dedupKey()` строит отпечаток по нормализованному тексту тела + сумме; `TransactionRepository.insertNotification()` под мьютексом проверяет окно ±30 сек и не создаёт вторую запись — вместо этого дополняет первую недостающими полями (если у одной копии не было заголовка/счёта, а у другой был).

### 1.2 Через "Поделиться чеком" — импорт PDF

`receipt/ReceiptImporter.kt` + `receipt/KaspiReceiptParser.kt` + `receipt/PdfOcr.kt`.

Пользователь жмёт "Поделиться" на чеке в Kaspi → приложение зарегистрировано в системе как получатель `ACTION_SEND`/`ACTION_SEND_MULTIPLE` для PDF (см. `AndroidManifest.xml`). Двухступенчатое извлечение текста:
1. Текстовый слой PDF (PDFBox) — быстро, работает для большинства чеков;
2. Если пусто или сумма не нашлась — OCR всей страницы через Tesseract (rus+eng, офлайн, модели в assets);
3. Если и это не дало сумму — отдельный проход OCR только по зоне баннера с крупной цифрой (там, где текст часто теряется).

Парсер чека вытягивает: сумму (по заголовку "Оплата совершена"/"Перевод успешно совершён" и т.д.), тип, контрагента, дату/время, счёт списания ("Откуда"). Для сервисных чеков (автобус, коммуналка) название сервиса берётся из шапки чека, а не из строки под суммой — там сидит уникальный номер квитанции на каждую поездку, который раньше плодил "новый мерчант" каждый раз.

**Слияние с уведомлением**: если чек описывает ту же операцию, что уже есть от push (совпадает сумма, разница ≤15 минут), `insertReceipt()` не создаёт вторую запись — дополняет существующую полным текстом чека, реальным мерчантом и счётом. Раньше это было главным источником задвоения расходов.

**Пакетный импорт**: `ui/screens/BatchImportScreen.kt` + `ReceiptImporter.importAll()` — выбор сразу нескольких PDF (`OpenMultipleDocuments`), последовательная обработка с прогресс-баром и сводкой (добавлено / дополнило уведомление / уже было / не прочиталось). `MainActivity` также принимает `ACTION_SEND_MULTIPLE` напрямую — если поделиться пачкой файлов из файлового менеджера, они обработаются тем же путём.

Защита от повторного импорта одного и того же чека: `isReceiptDuplicate()` по паре (timestamp, amount) для `source = RECEIPT`.

### 1.3 Вручную

`ui/screens/AddTransactionScreen.kt` + `AddTransactionViewModel.kt`.

Поле суммы — **не просто число, а калькулятор** (`util/AmountExpression.kt`): можно ввести `3600/2`, `-800`, `(500+1200)/2`, поддерживаются `+ - * / ( )`, оба десятичных разделителя, пробелы-разделители тысяч. При редактировании существующей операции (`EditTransactionSheet.kt`) ведущий оператор (`/2`, `-800`) применяется к уже сохранённой сумме — то есть на чеке 900 ₸ ввод `/2` даст 450. Под полем — живой предпросчёт результата (`AmountField.kt`), сохранить нельзя, пока выражение не сходится в число.

Категорию можно выбрать сразу в форме или оставить пустой — тогда сработает автокатегоризация/выученные правила, а если и они не справятся, запись уйдёт в очередь разбора. Экран прокручивается целиком (`verticalScroll` + `imePadding`) — раньше сетка категорий и кнопка "Сохранить" были недостижимы на невысоких экранах.

## 2. Категоризация

`data/Category.kt` — 11 категорий (Продукты, Кафе и еда, Транспорт, Покупки, Здоровье, Развлечения, Связь и коммуналка, Образование, Переводы, Доходы, Прочее).

`CategoryClassifier.classify()` — порядок применения:
1. **Выученное правило** (`CategoryRule`, таблица `category_rules`) — если пользователь хоть раз указал категорию для мерчанта, оно побеждает всё остальное, включая исходящие переводы (которые по умолчанию не классифицируются автоматически, так как перевод человеку может быть за что угодно);
2. Входящий перевод → всегда "Доходы";
3. Исходящий перевод без выученного правила → null, идёт в очередь разбора;
4. Список ключевых слов по категориям (`data/Category.kt`, `RULES`) — matching только с начала слова через regex с lookbehind на `\p{L}\p{N}` (обычный `\b` не работает с кириллицей в Java/Kotlin regex — это была реальная causa бага, когда "оси" матчилось внутри "гОСномер" и кидало автобусные билеты в "Коммуналку").

`data/CategoryRule.kt` — `MerchantKey.of()` нормализует название мерчанта: нижний регистр, `ё→е`, вырезание цифровых последовательностей длиной 3+ (чтобы номера чеков/квитанций не превращались в уникальный "мерчант" на каждую операцию), вырезание организационно-правовых форм (ООО/ИП/ТОО и т.д.) и служебных слов (квитанция/чек/№). Итоговый ключ — общий для "SMALL"/"Small", `ТОО "Скиф трейд"`/"Скиф Трейд" и т.п.

**Обучение**: `TransactionRepository.assignCategory()` (выбор в очереди разбора), `.update()` (правка категории в истории) и ручное добавление с выбранной категорией — все три пути вызывают `learn()`, который создаёт/обновляет `CategoryRule` и сразу применяет его ко всем ещё неразобранным операциям того же мерчанта (не только к текущей).

При обновлении приложения (`KaspiTrackerApp.onCreate`): `seedRulesFromHistory()` превращает уже расставленные вручную категории в правила (самая свежая по времени — победитель при конфликте), `backfillNotificationMerchants()` дочитывает мерчанта из старых записей, где парсер раньше не справлялся, `backfillCategories()` применяет правила и ключевые слова к тому, что осталось без категории. Всё идемпотентно — безопасно гонять повторно.

`ui/screens/CategorizeScreen.kt` — очередь "разбери один за другим": показывает следующую нерасклассифицированную операцию с суммой, тянет выбор категории, при выборе сразу переходит к следующей.

`ui/screens/CategoryRulesScreen.kt` — список всех выученных правил (мерчант → категория), с возможностью посмотреть, поправить (тап открывает выбор новой категории, применяется сразу к остаткам в очереди) или удалить правило (вернётся к классификации по ключевым словам).

## 3. Хранилище и защита данных

`data/AppDatabase.kt` — Room, версия 5, миграции 1→2→3→4→5 зарегистрированы явно (`addMigrations`). `fallbackToDestructiveMigration()` оставлен как последний рубеж — **важно**: любая новая версия схемы обязана получить свою `Migration`, иначе Room молча стирает всю историю при апдейте (это реально произошло один раз в процессе разработки — спасла резервная копия, снятая перед установкой).

Таблицы: `transactions`, `budgets`, `category_rules`.

### 3.1 Ручной бэкап

`data/Backup.kt` + `ui/screens/BackupScreen.kt`. Экспорт — весь `transactions` + `budgets` + `category_rules` в один JSON-файл, отдаётся через системное меню "Поделиться" (Telegram себе, облако, кабель — что угодно). Импорт — `OpenDocument`, слияние по отпечатку операции (`Backup.identityOf`: timestamp + сумма + источник + первые 120 символов текста), уже существующие записи пропускаются. Один и тот же файл можно накатывать многократно без задвоения. Правила категорий и бюджеты при импорте перезаписываются версией из файла.

### 3.2 Автоматический бэкап

`service/AutoBackup.kt` — WorkManager, `PeriodicWorkRequestBuilder` раз в 7 дней (первый запуск — через час после установки), пишет в `Downloads` через `MediaStore` (Android 10+) или во внутреннее файловое хранилище приложения на более старых версиях. Хранит последние 4 копии, старые удаляет сам. Статус последнего запуска виден на экране бэкапа.

## 4. Дедупликация — сводка

Три независимых механизма, каждый закрывает свой сценарий:

| Сценарий | Механизм | Где |
|---|---|---|
| Push приходит дважды (сводка + карточка) | Отпечаток текста + окно 30 сек + мьютекс | `insertNotification()` |
| Чек за операцию, уже пойманную push | Совпадение суммы в окне ±15 мин | `insertReceipt()` |
| Тот же чек прислан повторно | Совпадение (timestamp, amount) для source=RECEIPT | `isReceiptDuplicate()` |
| Тот же файл бэкапа накатан дважды | Отпечаток операции (Backup.identityOf) | `importBackup()` |

Ручные записи (`insert()`) никогда не дедуплицируются друг с другом — пользователь может осознанно добавить два одинаковых расхода.

## 6. Определение подписок

`data/Subscriptions.kt`, `SubscriptionDetector.detect()`. Группирует траты по нормализованному ключу мерчанта, ищет цикличность:
- сравнивает 2–3 последних платежа одного мерчанта, допуск на изменение суммы ±20% (подписка могла подорожать);
- недельный цикл (6–8 дней между платежами) требует **трёх** подтверждающих платежей подряд — двух недостаточно (иначе случайные две покупки в один и тот же день недели считались бы "еженедельной подпиской" — было такое ложное срабатывание на обычных походах в магазин);
- месячный цикл — 25–35 дней между двумя платежами;
- годовой — 355–375 дней;
- сервисы из захардкоженного списка (YouTube, Yandex Plus, Netflix, Spotify, Steam, Google/Apple подписки, годовое обслуживание карты и т.д.) показываются как "под вопросом" уже после одного платежа, до подтверждения повторением.

Сортировка — по стоимости в пересчёте на месяц (`monthlyCost`), не по сумме разового платежа: еженедельные 3000 ₸ (≈13000/мес) обгоняют ежемесячные 4990 ₸.

## 7. Уведомления и оповещения приложения

- **Доступ к уведомлениям** (`util/NotificationAccess.kt`) — банер на главном экране, если не выдан; перепроверяется при каждом возврате приложения на передний план.
- **Разрешение POST_NOTIFICATIONS** (Android 13+) запрашивается один раз при первом запуске (`MainActivity.onCreate`).
- **Оповещения о бюджете** (`service/BudgetAlerts.kt`) — системное уведомление при пересечении 80% лимита категории и повторно при превышении. Каждый уровень срабатывает не больше одного раза за месяц на категорию (состояние — в SharedPreferences), сброс естественным образом происходит со сменой месяца. Триггерится из `TransactionRepository.reportBudget()` после каждой вставки операции с категорией и лимитом.
- **BootReceiver** (`service/BootReceiver.kt`) — на некоторых прошивках (MIUI, EMUI) слушатель уведомлений отваливается после перезагрузки; получает `BOOT_COMPLETED`/`LOCKED_BOOT_COMPLETED`/`QUICKBOOT_POWERON` и делает `requestRebind`.

## 9. Прогноз и аналитика поведения

`util/MonthForecast.kt` — простая линейная проекция: (потрачено / прошедшие дни) × дней в месяце. `reliable = false` первые 3 дня месяца (одна крупная покупка в начале искажает прогноз до бессмысленности — UI честно пишет "прогноз появится через пару дней" вместо того, чтобы выдавать шум за число).

`HomeViewModel` считает "потрачено в этом месяце vs та же часть прошлого месяца" — не месяц целиком против неполного, а одинаковое число дней от начала месяца с обеих сторон, чтобы сравнение было корректным в любой день месяца.

- `AmountExpressionTest` (10) — калькулятор в поле суммы;

## 11. Чего ещё нет — roadmap

Приоритет сверху вниз. Отметка ⭐ — то, что даёт больше всего пользы на единицу работы.

### A. Целостность данных (фундамент, всё остальное на него опирается)

#### ⭐ A1. Сверка по остатку — автодетект пропущенных операций

Закрывает главную дыру приложения (QR-оплаты не приходят в push) **без выписки Kaspi**. В каждом push есть `Доступно: X ₸` — это готовый механизм контроля целостности.

Логика: между двумя соседними снимками баланса одной карты фактическая дельта обязана равняться сумме известных операций за этот промежуток. Не равняется — значит была операция, которую приложение не поймало.

```kotlin
/** Возвращает "призрачные" операции: дырки между снимками баланса. */
fun reconcile(
    snapshots: List<BalanceSnapshot>,   // по одному счёту, по возрастанию времени
    known: List<Transaction>,
    tolerance: Double = 100.0           // кэшбэк, проценты, округления
): List<GhostTx> = snapshots.zipWithNext().mapNotNull { (prev, curr) ->
    val expected = known
        .filter { it.account == prev.account && it.timestamp in (prev.timestamp + 1)..curr.timestamp }
        .sumOf { it.signedAmount }
    val gap = (curr.balance - prev.balance) - expected
    if (abs(gap) <= tolerance) null
    else GhostTx(prev.account, abs(gap), if (gap < 0) PURCHASE else INCOME, prev.timestamp, curr.timestamp)
}
```

UI: призрак падает в очередь разбора текстом «между 14:20 и 16:05 с Kaspi Gold ушло 1 200 ₸ — что это было?». Пользователь указывает мерчанта, шарит чек или помечает «не помню». Ложные срабатывания на кэшбэке гасятся допуском.

Побочный эффект: остаток на картах становится проверяемым, а не декоративным.

Заметка по реализации: снимки баланса **уже есть** в `transactions.balance` — отдельная таблица `balance_snapshots` не обязательна, деривации из существующих строк достаточно и не требует миграции. Деньги в схеме хранятся как `Double`, а не в тиынах; допуск сверки покрывает погрешность, полный переход на `Long` — отдельный крупный рефакторинг со своей миграцией.

#### ✅ A2. Детект переводов между своими счетами — СДЕЛАНО

Перевод с Gold на Депозит сейчас считается одновременно расходом и доходом. Это ломает «потрачено за месяц», прогноз, топ категорий и бюджеты — то есть цифры на главном экране прямо сейчас неверны, если такие переводы были.

```kotlin
private const val SELF_WINDOW_MS = 3 * 60_000L

fun matchSelfTransfer(tx: Transaction, recent: List<Transaction>, myAccounts: Set<String>) =
    recent.firstOrNull {
        it.amount == tx.amount &&
        it.type.isOutgoing != tx.type.isOutgoing &&
        it.account != tx.account &&
        it.account in myAccounts &&
        abs(it.timestamp - tx.timestamp) <= SELF_WINDOW_MS
    }
```

Нужен флаг `excludedFromStats: Boolean` в `Transaction` — общий для внутренних переводов, возвратов и ошибочных записей. Все агрегаты (`HomeViewModel`, `AnalyticsViewModel`, бюджеты, подписки) фильтруют по нему. Реестр «своих счетов» набирается автоматически из заголовков push плюс ручное подтверждение.

#### ✅ A3. Watchdog слушателя уведомлений — СДЕЛАНО

Самый вероятный сценарий тихой поломки: Samsung усыпляет процесс, push перестают приходить, приложение выглядит рабочим.

Порог молчания — адаптивный, а не константа:

```kotlin
val limit = min(p90(intervalsBetweenKaspiPush) * 2, 24.hours.inWholeMilliseconds)
```

Восстановление двухступенчатое, потому что на Samsung `requestRebind()` в одиночку часто не срабатывает:

```kotlin
val cn = ComponentName(ctx, KaspiNotificationListener::class.java)
NotificationListenerService.requestRebind(cn)   // мягкий путь
// жёсткий: передёрнуть компонент, ОС пересоздаст биндинг
pm.setComponentEnabledSetting(cn, COMPONENT_ENABLED_STATE_DISABLED, DONT_KILL_APP)
pm.setComponentEnabledSetting(cn, COMPONENT_ENABLED_STATE_ENABLED, DONT_KILL_APP)
```

Плюс `lastNotificationAt` в SharedPreferences на каждый push, баннер на главном («последняя операция поймана 3 дня назад — проверьте доступ») и разовый диалог с deep-link в Settings → Battery → Unrestricted при первом запуске.

### B. Инфраструктура

#### ✅ F4. Git — СДЕЛАНО (CI пока нет)

Репозиторий создан, два коммита, `.gitignore` исключает `local.properties`, `.idea`, сборки, а также `*.db`/`*.pdf` — чтобы личные финансовые данные не попали в историю. ### C. Деньги вперёд, а не назад

#### C1. Safe-to-spend — «сколько можно тратить в день»

Самая полезная цифра в личных финансах, и все данные для неё уже есть:

```
доступно = сумма остатков по картам
         − подписки с датой списания до конца месяца
         − обязательные платежи (аренда, кредит, коммуналка)
         − цели накоплений (взнос этого месяца)
на день  = доступно / оставшиеся дни
```

На главный экран — вместо линейного прогноза или рядом с ним. Цвет: зелёный, если сегодняшние траты ниже нормы, коралловый — выше. Ежедневное уведомление в 21:00 «сегодня −4 200 при норме 5 800».

Плюс **календарь**: месяц квадратиками, цвет по дню (ниже/выше нормы), тап по дню — сумма трат за него.

#### C3. Цели накоплений (sinking funds)

Цель, сумма, срок → «откладывать 35 000/мес». Прогресс пополняется вручную или автоматически по переводам на депозитную карту. Влияет на safe-to-spend (C1).

#### D1. Прогноз v2

Текущая линейная проекция шумит на регулярных платежах. Честнее:

```
прогноз = уже потрачено
        + Σ(запланированные платежи с датой в остатке месяца)
        + медиана дневных переменных трат × оставшиеся дни (с поправкой на день недели)
```

Плюс интервал вместо точки: «ожидается 280–340 тыс». Медиана вместо среднего убирает влияние одной крупной покупки — ровно та проблема, из-за которой прогноз сейчас отключён первые 3 дня месяца.

### E. Скорость и удобство

- **E1. Виджет + QS-плитка + App Shortcut.** Наличная трата должна вводиться в два тапа с локскрина. Glance для виджета (Compose-подобный API), `TileService` для шторки. Виджет показывает «сегодня / за месяц / safe-to-spend».
- **E2. Свайпы в очереди разбора.** Свайп влево/вправо → две самые вероятные категории, тап-холд → полный список. Разбор 50 операций из 5 минут превращается в 40 секунд.
- **E3. Поиск с операторами в Истории**: `>5000 кафе за неделю`, `Магнум январь`. Парсер запроса строк на 60, фильтры ложатся на существующий `HistoryViewModel`.
- **E5. Material You + тёмная тема.** `dynamicColorScheme()` с фолбэком на фирменные акценты; существующая дизайн-система от этого только выиграет.
- **E6. Полировка Истории и Журнала под `Decor.kt`** — сейчас там базовые карточки без цветовых акцентов и деталей, которые уже есть на Главном/Аналитике/Бюджетах.
- **E7. Экспорт отчёта в PDF/XLSX** за период — не только CSV. Плюс шаринг картинки-сводки за месяц.

### F. Прочее

- **Экран «Люди».** Данные есть (переводы с именами контрагентов), сводки по человеку (отдал/получил/чистый баланс) — нет.
- **Фильтр рекламных push.** ~60 записей вида «Оформим покупку?👀» осели в базе как PURCHASE без суммы — в деньги не лезут, но засоряют Журнал уведомлений.
- **UI-тесты (Compose).** Логика покрыта хорошо, ни один экран не проверен автоматическим UI-тестом.
- **Проваливание из Аналитики в Историю по мерчанту** (сейчас только по категории+периоду).
- **Настоящий сплит операции** с созданием второй записи (сейчас только формула в поле суммы, что не то же самое).
- **Импорт выписки Kaspi (PDF).** Полностью закрыл бы пробел с QR-оплатами, но требует образца файла — без него верстку таблицы не угадать. После A1 приоритет падает: сверка по остатку ловит те же пропуски без выписки.
- **Множественная валюта** — не приоритет, у Kaspi всё в ₸.

## 12. Технические заметки на будущее

- **Миграции БД — не пропускать.** Любой новый `@Entity`/столбец → новая `Migration` в `AppDatabase.kt` → регистрация в `addMigrations(...)`. Иначе `fallbackToDestructiveMigration()` сотрёт всё молча.
- **Перед установкой сборки, меняющей схему БД, — снять бэкап базы** (`adb exec-out run-as ... cat databases/kaspi_tracker.db`), даже если миграция вроде бы написана правильно.
- Java/Kotlin `\b` в regex не работает с кириллицей (ASCII-only) — использовать lookbehind/lookahead на `\p{L}\p{N}`, как в `KaspiNotificationParser.MERCHANT_REGEX` и `Category.compile()`.
- Батарея Samsung агрессивно душит фоновые сервисы — приложение должно быть в исключениях (Настройки → Батарея → Неконтролируемые приложения), иначе `KaspiNotificationListener` может быть убит без предупреждения.
- При переносе на новый телефон доступ к уведомлениям нужно выдавать заново вручную — не переносится автоматически ни бэкапом, ни `adb`.
